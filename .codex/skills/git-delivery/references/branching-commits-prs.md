# Branching, Commits and Pull Requests

Prefer short-lived branches and small independently reviewable changes unless the repository has a justified alternative. Inspect existing history before imposing a convention. Commits should group one coherent intent, avoid unrelated formatting/generated churn, and include meaningful messages; Conventional Commits are useful when changelog/version automation depends on them but are not inherently superior. Pull requests should explain problem, approach, risk, verification and migration/rollback implications proportional to impact. Required checks should cover real failure modes. Reviews focus on correctness, architecture, security, tests and operational effects rather than style already automated by tooling. Avoid force-pushing shared/protected history without explicit coordination. Draft PRs are appropriate while verification is incomplete; production-bound work becomes ready only after its required gates pass.
