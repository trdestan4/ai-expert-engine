# Release Versioning and Changelog

Choose versioning that matches how consumers experience compatibility. Semantic Versioning is useful for libraries/APIs with meaningful public compatibility contracts; deploy-every-commit applications may rely more on immutable deployment IDs plus release notes. Tags should identify exact source commits and, where relevant, corresponding artifacts. Release notes prioritize user/operator impact, migrations, deprecations, breaking changes and rollback considerations over raw commit lists. Changelogs should be generated from structured commits only if the convention is actually enforced; otherwise curate meaningful entries. Deprecations need timeline, replacement and migration path. Never label a release backward-compatible merely because compilation succeeds. Database, API, auth, billing and workflow changes may break operational behavior without changing types.
