# Incident Response and Runbooks

An incident process should establish severity, incident lead/ownership, immediate containment, communication and evidence preservation before deep optimization. Start from customer impact and recent change history, then inspect logs/metrics/traces and dependencies. Prefer reversible mitigation—rollback, feature disable, traffic shift, rate limit or dependency bypass—when it reduces harm safely. Runbooks should name concrete dashboards, queries, commands or checks; include prerequisites, safe/unsafe actions, escalation contacts/roles and post-action verification. Record timestamps and decisions for later analysis. Postmortems should be technically blameless and identify contributing conditions, detection gaps, recovery friction and durable corrective actions with owners. A runbook that has never been exercised should be treated as partially unverified.
