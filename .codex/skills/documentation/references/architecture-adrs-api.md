# Architecture, ADRs and API Documentation

Architecture documentation should describe system boundaries, major components, data/control flow, external dependencies, runtime/deployment shape and the invariants future changes must preserve. Diagrams should communicate relationships rather than decorate documents. Architecture Decision Records are appropriate for consequential choices: include context, decision, alternatives/tradeoffs, consequences and status. Do not use ADRs for every minor implementation detail. API documentation should align with the actual contract and version; prefer OpenAPI/GraphQL/source-linked generation where it reduces drift, while retaining human explanations for authentication, pagination, errors, examples and lifecycle semantics. Public interfaces need deprecation/migration guidance. Documentation should link to ownership and source files so maintainers can verify it against code rather than treating prose as unquestionable truth.
