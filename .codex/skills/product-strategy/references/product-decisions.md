# Product Decision Framework

Use when product directions compete or scope must be prioritized under uncertainty.

## Frame the decision

State the user/business outcome, hard constraints, reversible vs irreversible aspects, current evidence and what happens if the decision is wrong. Separate “must be true” from preference.

Generate only viable options—usually two or three. Include “do nothing / defer / instrument first” when it is genuinely viable. Do not add an obviously bad option to make a preferred answer look stronger.

## Evaluation dimensions

Select only dimensions that can change the choice:
- user value / job completion;
- business value and unit economics;
- trust/safety/privacy impact;
- evidence strength and uncertainty;
- strategic differentiation;
- implementation and operational cost;
- maintenance/content/data burden;
- time-to-value;
- reversibility and migration cost;
- measurement clarity;
- dependency and organizational fit.

Weights are contextual. Authorization or payment integrity outranks cosmetic convenience. A reversible experiment can tolerate more uncertainty than a destructive data-model commitment.

## Prioritization

Use Core / Supporting / Optional / Noise for product scope. For backlogs, prefer an explicit outcome/opportunity model over generic RICE scoring when inputs are mostly guesses. If using RICE/WSJF/etc., expose the assumptions and perform sensitivity checks: would the ranking change if a noisy estimate moved 2x?

Reject feature accumulation that does not improve the primary job, trust, differentiation or measurable outcome.

## Pricing and monetization decisions

When relevant, distinguish value metric, packaging, entitlement, billing implementation and market price—they are not the same decision. Evaluate willingness-to-pay evidence, customer segmentation, marginal cost, abuse surface, upgrade/downgrade behavior and operational support burden. Avoid pricing solely by competitor averages.

## Build vs buy

Compare strategic differentiation, maturity/security/compliance needs, integration surface, switching cost, data/control requirements, vendor lock-in, operating cost and internal competence. Commodity auth/payments/email/search infrastructure often favors mature providers; core differentiating workflows may justify ownership. “No vendor dependency” is not automatically cheaper.

## Decision record

Record:
- selected option;
- decisive reasons and strongest evidence;
- meaningful downside accepted;
- assumptions/unknowns;
- validation or instrumentation plan;
- condition that would justify revisiting it.

## Anti-patterns

Avoid:
- newest technology by default;
- speculative scale with no requirement;
- fictional personas as evidence;
- vanity metrics;
- roadmap as a list of outputs with no outcomes;
- A/B tests for correctness/safety obligations;
- false precision in market size or prioritization scores;
- irreversible commitments before cheaper learning when learning is possible.

A product direction should be explainable without “looks premium/modern.” If the rationale collapses to visual taste, product strategy is not yet doing its job.
