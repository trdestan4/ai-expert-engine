# Deployment Strategies and Rollbacks

Choose rollout strategy from compatibility and blast radius. Simple replacement works for low-risk, backward-compatible changes. Canary/progressive rollout is useful when traffic can be segmented and telemetry can detect regressions quickly. Blue/green is valuable when environments can run in parallel and data/schema compatibility is understood. Feature flags can decouple code deployment from feature exposure but require ownership, expiry and safe defaults. Database changes often need expand/backfill/switch/contract sequencing so old and new code overlap safely. Define rollback before release: previous artifact promotion, alias reversal, feature disable, application revert, database roll-forward or restore. Never call rollback safe if irreversible data mutation already occurred. After any rollback/roll-forward, verify health, migration state, queues/jobs and external integrations.
